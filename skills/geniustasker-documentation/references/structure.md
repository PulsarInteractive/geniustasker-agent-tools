# Organize for people and agents

Adapt this suggested structure to the existing library; do not replace a user’s
taxonomy simply to match a template.

| Category     | Typical children                                           |
| ------------ | ---------------------------------------------------------- |
| Overview     | Product intent, audience, glossary and current constraints |
| Product      | Flows, feature definitions and acceptance criteria         |
| Architecture | Components, data ownership, permissions and integrations   |
| Decisions    | Context, decision, alternatives and consequences           |
| Visuals      | Interface, Maps, Items, Characters and Mockups             |
| Resources    | Stable media IDs, captions, provenance and variants        |
| Validation   | Dated checks, evidence and unresolved limits               |

Every category can contain nested folders and several documents. A page can
introduce child documents. Use parent IDs, order and concise titles; `kind` and
`section` are configurable labels. Keep deep details in focused children rather
than one enormous page. Preserve stable block IDs across edits.

Separate approved behavior, proposals and dated validation. Record source
provenance instead of presenting an imported screenshot as implementation proof.
Use inherited content roles for restricted branches. A folder name or a local
export setting does not establish access control.

Reuse one resource ID across related pages and node thumbnails. Compare existing
and proposed media before uploading. Typed Graph relations connect concepts
across products; resolve borrowed Memory under its own permissions. Do not make
projects mandatory owners of Memory or Graph content.
